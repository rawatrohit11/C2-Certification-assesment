# Data Model

**Status:** Approved for implementation  
**Sources:** `spec/requirements.md`, `spec/state-machine.md`  
**Last updated:** 2026-09-23

## 1. Scope

The initial model contains tickets and their comments. Users, attachments, status-history records, and deletion are out of scope.

## 2. Ticket

Persist tickets in `tickets`.

- `id` — UUID, primary key, generated by the server, immutable.
- `title` — variable text, required, trimmed, 1–200 characters.
- `description` — variable text, required, trimmed, 1–5000 characters.
- `priority` — required enum string: `LOW`, `MEDIUM`, `HIGH`, or `URGENT`.
- `status` — required enum string: `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`, or `CANCELLED`.
- `assignee` — nullable variable text; when present, trimmed and 1–100 characters.
- `created_at` — required UTC instant, generated by the server, immutable.
- `updated_at` — required UTC instant, generated by the server and changed on successful ticket field or status updates.

Rules:

- New tickets always persist as `OPEN`.
- No database or API default is defined for priority; the client must supply it.
- Empty or whitespace-only assignee input is normalized to null.
- Status is stored as a string, never as an enum ordinal.
- There is no optimistic-lock version column in the initial model.
- Adding a comment does not update the parent ticket row or its `updated_at`; the comment has its own `created_at`.

## 3. Comment

Persist comments in `ticket_comments`.

- `id` — UUID, primary key, generated by the server, immutable.
- `ticket_id` — required UUID foreign key to `tickets.id`.
- `body` — variable text, required, trimmed, 1–2000 characters.
- `created_at` — required UTC instant, generated by the server, immutable.

Rules:

- Comments are append-only through the public API.
- No author is stored because authentication and user accounts are out of scope.
- Comments are returned oldest-first; use `created_at`, then `id`, for deterministic ordering.
- Comments may be added to tickets in any status.
- Ticket deletion is out of scope, so no public cascade behavior is exposed.

## 4. Relationships

- One ticket has zero or more comments.
- Every comment belongs to exactly one ticket.
- A comment cannot exist without its ticket.

## 5. Enumerations

### TicketPriority

- `LOW`
- `MEDIUM`
- `HIGH`
- `URGENT`

### TicketStatus

- `OPEN`
- `IN_PROGRESS`
- `RESOLVED`
- `CLOSED`
- `CANCELLED`

The application and database constraints must use exactly these uppercase values.

## 6. Indexes

Required:

- Primary-key indexes on both IDs.
- Index on `ticket_comments(ticket_id, created_at, id)` for ordered detail reads.
- Index on `tickets(status, created_at, id)` for status-filtered newest-first pages.
- Index on `tickets(created_at, id)` for unfiltered newest-first pages.

Keyword search uses case-insensitive substring matching over title and description. A specialized PostgreSQL search index is not required for the initial assessment-sized data set. If performance evidence later requires one, document the PostgreSQL-specific migration before adding it.

## 7. Pagination ordering

Ticket pages use deterministic newest-first ordering:

1. `created_at` descending.
2. `id` descending as a tie-breaker.

The API uses zero-based page numbers, default size 20, and maximum size 100 as defined in `api-contract.md`.

## 8. Timestamp policy

- Application-facing timestamps are UTC ISO 8601 values.
- Backend domain timestamps use `Instant`.
- PostgreSQL columns must preserve timezone-aware instants.
- Tests use a controllable clock where timestamp values affect assertions.

## 9. Persistence profiles

- Default runtime: PostgreSQL.
- Automated tests: H2 where SQL behavior is compatible.
- PostgreSQL-backed integration tests are required for database behavior that H2 cannot prove.
- Restart persistence for AC-011 must use PostgreSQL or another explicitly durable profile, never in-memory H2.

## 10. Data invariants

- Required ticket fields cannot be null.
- Required comment fields cannot be null.
- Enum columns contain only recognized values.
- Field lengths satisfy section 2 and section 3.
- Comment foreign keys reference existing tickets.
- A rejected status transition changes no row.
